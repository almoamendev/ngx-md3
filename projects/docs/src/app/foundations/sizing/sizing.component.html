Sizing & scaling

Every size in the library is relative to a font-size. Components size themselves in em, the breakpoints are in rem, and md3.scss sets html {{ '{' }} font-size: 16px {{ '}' }}, so 1rem is 16dp and the sizes match the Material Design specs. That gives you two levers: the html font-size scales the whole UI, layout included, and the --md3-scale custom property scales the components — everywhere, in one part of the page, or one at a time.

How a component is sized

Each component sets its font-size to --md3-scale times 1rem on its host element and measures everything else — height, padding, gaps, icons, the label — in em of that font-size. At the default scale of 1 a button is 40px tall; at 1.25 it is 50px, with every part kept in proportion. Tokens such as shape and elevation are in em too, so a corner radius or a shadow follows the component it is on. The type scale and badges read --md3-scale the same way.

Scaling the whole UI

Change the font-size of html after importing md3.scss. Every component, the typography scale and the layout grid follow it.

md3.scss uses 16px rather than 100%, so the library looks the same in every browser by default. Setting 100% instead lets the font size the user picked in their browser settings scale the UI.

The breakpoints scale too

The window size classes are measured in rem, so a larger root font-size moves them with the rest of the UI. A window 1280px wide is large at 16px (80rem) but expanded at 20px (64rem): the UI is bigger, so the layout switches to the one for a smaller window, exactly as it would on a smaller screen. Media queries can't do this. Inside a @media condition, rem and em resolve against the browser's default font size, not against html {{ '{' }} font-size {{ '}' }}. So the library uses none for its breakpoints:

  • md-grid.scss makes html a query container named md-viewport and declares the grid tokens in @container rules. A container query resolves rem against the root's computed font-size.
  • LayoutService.widthClass() and heightClass(), which the navigation, the scaffold and the other responsive components read, divide the root's width and the window's height by the root font-size. They re-measure when the window resizes and when the root font-size changes, whatever changes it.

Both measure the same box, the html element, against the same thresholds, so a component that switches layout and the grid that adds columns always switch at the same pixel.

Scaling components with --md3-scale

--md3-scale is a plain number, 1 by default. Like any custom property it is inherited, so set it on a component to scale that component, or on any element to scale every component inside it. A component inside a scaled region can set its own value again.

It is always a factor of 1rem, never of the surrounding size, so scales don't compound: a button at 1.25 inside a card at 1.25 is 1.25 times its normal size, the same as the card's own parts. And since it is a custom property, any selector works — there is no specificity to beat.

Unlike the html font-size, --md3-scale leaves the layout alone: the breakpoints, the grid and the default text size of body only follow the root font-size. Use it to make components larger or more compact, and the root font-size to scale everything.

Overlays

Dialogs, sheets, menus and snackbars render at the end of body, outside the element that opened them, so they follow the --md3-scale of the root, not of the region they were opened from. Each service takes a scale option for a different one:

A menu also accepts 'inherit', which copies the scale of the element it opens from. Submenus and the options of a select field use it by default, so they always match their trigger. The margins that keep a dialog or a menu away from the window edges follow the root scale, never an overlay's own, so every dialog sits in the same frame.

Scrolling and the scrollbar

In the scaffold, the window never scrolls — md3.scss sets html and body to the window height, and the content scrolls inside its panes. The html element never gets a scrollbar, so the width the breakpoints measure is always the full width of the window.

If you change that, so the window scrolls the document as a classic page does, a classic scrollbar (Windows, Linux, macOS with Always show scrollbars) takes about 15–17px from html. Phones and macOS by default use overlay scrollbars, which take no space, and are not affected. Two things follow:

  • The breakpoints measure the width without the scrollbar. That is consistent between the components and the grid, but a window is one class narrower than its outer size suggests over those few pixels.
  • Near a breakpoint the layout can flip back and forth. A switch to a narrower layout makes the page taller, a scrollbar appears, html loses its width, and the class can change again. You see a flicker, a layout stuck in the wrong class, or a ResizeObserver loop message in the console.
