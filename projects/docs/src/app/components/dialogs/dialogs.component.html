  • Dialogs are custom components injected in the page using dialog service.
  • When creating your custom dialog component, you can optionally use md3-dialog-header, md3-dialog-body and md3-dialog-actions.
  • On open, focus moves to the first focusable element inside the dialog (or the dialog surface itself if none is found). On close, focus returns to the element that triggered the dialog.
  • While a dialog is open, focus stays trapped inside it and the rest of the page is hidden from assistive technology.
  • Unless disableCloseEvents is set, clicking the scrim or pressing Escape closes the dialog with no result. Escape combined with a modifier key is ignored.
  • The dialog is rendered through the CDK dialog (@angular/cdk/dialog), so it plays well with other CDK overlays such as menus and sheets.
  • Opening a dialog while another one is open closes the open one by default. Use previousDialog: 'hide' to keep it alive instead — it comes back with the opening animation once the dialog above it closes.
  • Dialogs replace each other in sequence rather than at the same time: the one on screen starts leaving, and the next one animates in 160ms later. The same head start applies in reverse, when a hidden dialog comes back. The scrim is handed over between them, so the page behind keeps a single, steady scrim.
  • A hidden dialog keeps its component instance, so scroll position, form state and subscriptions are preserved. It is marked inert while hidden, so it takes no focus and is skipped by screen readers.
  • Dialogs can also be hidden on purpose, to let the page be used without losing the dialog: dialogRef.hide() sends one away with the closing animation, dialogRef.show() brings it back with the opening one. hideAll() and showAll() do the same for everything on screen, the full screen dialog included.
  • While every dialog is hidden the page belongs to the user again: the scrim is gone, scrolling is released, the page is exposed to assistive technology once more, and focus goes back to the element that opened the first dialog. A hidden dialog also ignores the Escape key, since it is not the dialog the key is meant for.
  • Page scrolling stays blocked for as long as one dialog of the stack is on screen, and focus returns to the element that opened the first dialog once the last one closes.

Full screen dialog

A full screen dialog covers the window and holds a whole task rather than a single decision. It has no scrim, since there is nothing left to dim.

Its content is an md3-layout, which places the same regions the scaffold does — the bar rows, the rail columns and the start and end panes. So the dialog holds an app bar, a toolbar and a side sheet the same way a page does, and a side sheet opened while the dialog is up lands inside it.

  • Only one full screen dialog can be open at a time. Opening another one replaces it, along with anything stacked on top of it. openFullScreen() therefore takes a FullScreenDialogConfig, which is the dialog configuration without previousDialog.
  • While it is open, openSideSheet() targets the panes of the dialog's layout, so a sheet opens beside the main pane and under the app bar, exactly as it does on a page. When the dialog closes, the page scaffold takes the outlets back and the sheets opened inside the dialog go with it.
  • Regular dialogs open on top of a full screen dialog and never hide or close it, whatever previousDialog says. They still replace each other as usual.
  • The content of a full screen dialog is an md3-layout. It places the same regions the scaffold does, so the dialog takes an md3-app-bar in a bar region, a md3-toolbar in a bar or a rail region, and md3-dialog-body in the main pane, which scrolls. There is no bottom action bar — the trailing app bar button is the confirming action.
  • The layout is not optional. A content root that does not start with md3-layout gets a warning in development mode, because the dialog then has no bar and no rail region and the content does not scroll on its own. The dialog still falls back to panes of its own in that case, so a side sheet never opens behind it where nobody can see it.
  • The app bar takes an icon button marked md3-app-bar-leading to leave the dialog and an action marked md3-app-bar-trailing. The headline is the bar-title input. A bar inside a dialog carries no banner role, because the banner of the document is the app bar of the page behind it.
  • A full screen dialog hides and shows like any other one, with the whole task it holds still in place. It keeps the side sheet outlets while it is hidden, so a side sheet opened in the meantime lands in the dialog and comes back with it.
