Toolbar

Toolbars hold the actions of the current page. md3-toolbar is projected into a md3-scaffold region, and the region decides where it goes and which way it runs — a bar region gives a horizontal toolbar, and a rail region gives a vertical one. It reads its scroll state from the scaffold's main pane through LayoutService, so no extra wiring is needed.

The Material Design 3 specification replaces the bottom app bar with the docked toolbar. Use toolbar-type="docked" where you would have used a bottom app bar.

Placement

Put the scaffold region attribute on the toolbar itself. The region sets the default orientation, and it decides whether the toolbar covers the content or reserves its own space.

Region Default orientation Space
md3-scaffold-bar="bottom" horizontal Floating: covers the content. The scaffold pads the main pane by what it covers.
Docked: reserves its own row.
md3-scaffold-bar="top" horizontal Same as the bottom bar.
md3-scaffold-rail="leading" vertical Reserves its own column. Nothing goes behind it, so no padding is necessary.
md3-scaffold-rail="trailing" vertical Same as the leading rail.
No region horizontal The toolbar is a plain block. Position it yourself.

A docked toolbar spans the full window width, so it belongs in a bar region only. A vertical toolbar ignores scroll-action. Both give a development-mode warning if you configure them otherwise.

Content slots

Name Renders when
(default) Always. Icon buttons, buttons, button groups and text fields, in the order you write them. Use md3-button-group to group related actions.
[md3-fab] A projected md3-fab sits beside the container as its own surface, on the side that fab-position names.
[md3-toolbar-persistent] A plain attribute on any item in the default slot. The item stays on the screen when scroll-action="collapse" hides the others.

API

Name Type Default
toolbar-type

Floating draws a rounded, elevated container with a 16px outside margin. Docked fills its region with square corners and no elevation.

 input<ToolbarType> floating
toolbar-color

Standard uses a surface container. Vibrant uses a primary container, and remaps the colors of the buttons inside it.

 input<ToolbarColor> standard
orientation

Leave it unset to follow the scaffold region. An explicit value always wins.

 input<ToolbarOrientation | null> null
alignment

Where the item row sits inside the container. Visible on a docked toolbar; a floating container is as wide as its content, so it has no free space to align in.

 input<ToolbarAlignment> center
scroll-action

What happens when the scaffold's main pane scrolls down. Hide moves the toolbar out of the region. Collapse keeps the FAB and the marked items only.

 input<ToolbarScrollAction> none
fab-position

Which side of the container a projected FAB sits on.

 input<'start' | 'end'> end
expanded

The collapse state, as a two-way model. Scrolling writes to it, and you can read or set it yourself.

 model<boolean> true

Published by the scaffold. The main pane pads itself by these values, so a floating bar never hides the content permanently. Set them to 0 on a page that needs full-bleed content.

 0
  • The toolbar has one item region. Group related actions with md3-button-group rather than with separate leading and trailing slots.
  • scroll-action="collapse" needs something to keep: a projected FAB, or at least one item with md3-toolbar-persistent. With neither, the toolbar hides instead, and warns in development mode.
  • The toolbar never hides or collapses while it holds the focus, and it expands again as soon as the focus enters it. This keeps every control reachable for keyboard and screen-reader users.
  • A floating toolbar reports its expanded height at all times, even while it is hidden or collapsed. The content padding therefore stays still while the user scrolls, and snackbars stay above it.
  • scroll-action keys off LayoutService.mainScrollTop(), which is populated by whichever element carries md3-scaffold-pane="main" — outside a scaffold, the toolbar will not react to scrolling at all.
